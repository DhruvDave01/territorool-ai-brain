1. Architecture overview

TerriTool monetizes mobile users through RevenueCat (react-native-purchases), which unifies Apple App Store and Google Play into one subscriber model. Your Laravel backend owns package names, credits, and trial flags—the mobile app reads that via getusercredit and getuserstatus.

User → TerriTool App → App Store / Play Store → RevenueCat → Webhook → Laravel DB
                              ↑                                    ↓
                         Purchase UI                    getusercredit / getuserstatus

Principle: Webhook + subscriber sync is the source of truth for paid state. Client revenuecate-success is a optional fast-path nudge after purchase.

2. RevenueCat identity & mobile integration

App user ID format

Each TerriTool user gets a unique RevenueCat customer:

app_user_id = {numericUserId}_{email}

Example: 12345_user@example.com

Set on register/login via RevenueCatService.identifyUser() → Purchases.logIn(appUserId).

Webhook rule: Parse numeric user id from prefix before first _ when the prefix is digits.

Current client → backend flows

Flow Store purchase Backend call
Register + first purchase Yes POST /api/revenuecate-success (app_user_id)
Login (inactive trial) — GET getusercredit → SubscriptionGate
Settings Base ↔ Pro Yes getuserstatus + getusercredit only (no revenuecate-success today)
Logout — Purchases.logOut() → next login switches RC user

API keys (mobile)

Platform Key prefix
iOS appl_…
Android goog_…

Use matching RevenueCat projects/environments for staging vs production.

3. Android vs iOS: which webhook event fires when?

RevenueCat sends the same event types for both stores. Payload includes:

"store": "APP_STORE"   // iOS
"store": "PLAY_STORE"  // Android

Backend should not branch on store for package assignment—map by product_id and active entitlements. Store field is for logging/analytics only. Timing differs for some downgrades (especially Android deferred).

Event reference

Event Meaning
INITIAL_PURCHASE First subscription or trial started
RENEWAL Auto-renewal billing cycle
PRODUCT_CHANGE Upgrade, downgrade, or SKU change
CANCELLATION Auto-renew turned off (access often until period end)
UNCANCELLATION Auto-renew re-enabled before expiry
EXPIRATION Subscription ended
BILLING_ISSUE Payment failed
TEST Sandbox / dashboard test ping

Backend rule on every webhook

1. Verify Authorization header
2. Idempotency check on event.id

4. Map active product_id → package_name + credits
5. Write DB — subscriber snapshot wins over event type alone

4. Ten accounts, one device, one payment method

Question: Register emails user1@ … user10@ on the same device with the same payment method — what happens?

Short answer

  • 10 separate TerriTool accounts and 10 RevenueCat customers are created.
  • One Apple ID / Google account (same device + card) controls store trials and paid subscriptions.
  • Store intro trials do not repeat for accounts 2–10 on the same store account.
  • A paid subscription belongs to the store account, linked in RevenueCat to whoever was logged in at purchase time—not automatically to all 10 emails.

Per-account isolation (app + RevenueCat)

Account Backend user id RevenueCat app_user_id
user1@… 1 1_user1@…
user2@… 2 2_user2@…
… … …
user10@… 10 10_user10@…

On each login: Purchases.logIn("{id}_{email}"). Logout: Purchases.logOut().

Same device_token (FCM) is sent on every register/login—backend may use this for push or fraud detection (server-side).

What Apple / Google enforce

Layer Same device + same card
Store account Usually one Apple ID / Google account
Intro free trial Once per subscription group / offer rules
Paid subscription Typically one active sub per product group per store account
TerriTool emails Independent in your DB

Scenario A — each account tries store “7-day free trial”

user1@… → RC logIn(1_…) → Store trial → often SUCCESS
user2@… → RC logIn(2_…) → Store trial → often DENIED (no intro)
…
user10@… → same

TerriTool may still create all accounts; billing trial is store-limited.

Scenario B — user1 pays Pro; user2 logs in

user1 paid → entitlement on RC customer 1_user1@…
Logout → logIn(2_user2@…) → NO entitlement
user2 must pay separately OR use Restore (see Scenario C)

Scenario C — user2 taps “Restore purchases”

Restore uses the store account (same as user1). The store subscription may attach to current RC user (2_user2@…)—potential wrong-account entitlement if backend does not validate original purchaser.

Practical outcome table

# Email Store intro trial TerriTool (typical)
1 user1@… Often works Free trial / Free Package
2–10 user2@…–user10@… Usually blocked Account exists; paywall or full price
Any One paid sub on store One billing relationship Only linked RC app_user_id unless Restore moves it

Risks

  1. Trial farming — many emails, one device
  2. Restore hijacking — subscription restored onto wrong TerriTool user
  3. Duplicate device_token — 10 registrations from one device
  4. Webhook — must map purchase to correct app_user_id only

5. Giving a trial to all ten emails

Question: What if you want to give a trial to all 10 emails?

What you cannot do

Ten Apple/Google store intro trials on the same device + same payment method — not possible. Stores allow roughly one intro offer per store account per subscription group.

The app button “Start 7-day free trial” calls Purchases.purchasePackage — that uses the store intro offer.

What you can do

Trials for all 10 must be TerriTool-controlled (backend or RevenueCat promotional)—not ten store intro offers.

Option A — Backend-only trial (recommended simplest)

Grant trial in your database on registration without store purchase.

On mobileregistration success:

  • package_name = "Free Package"
  • free_trial_status = active (1 / true)
  • subscription_date = today + 7 days
  • Grant trial credits (e.g. 60)
  • User enters app without completing IAP

When trial ends:

  • Set free_trial_status = inactive
  • App shows SubscriptionGate
  • User must complete real App Store / Play purchase
Pros Cons
Each email gets 7 days Not a store subscription until conversion
Same device OK Fraud risk (10 × credits)
No store trial limit Need device/abuse rules

Option B — RevenueCat promotional entitlement

Backend calls RevenueCat REST API to grant time-limited entitlement per app_user_id without store intro:

Register user3@… → logIn(3_user3@…) → Backend grants RC promotional entitlement 7 days
→ Backend sets Free Package + credits
Pros Cons
Clean per-user RC record Requires RC API integration
Webhook-friendly More engineering

Option C — Hybrid (production pattern)

Account Trial source
First on device Store trial via paywall (current flow)
Same device, emails 2–10 Backend-only or RC promotional trial

Backend checks device_token / device fingerprint:

  • First registration → normal paywall
  • Additional accounts on same device → backend grants 7-day Free Package without store intro

Changes required vs today

Area Today For 10 trials
Register paywall Store purchase → “trial activated” Allow dashboard when backend grants trial
revenuecate-success After store purchase Also from register API or not required for backend trials
free_trial_status From getusercredit Set active per new user (with rules)
SubscriptionGate Blocks if inactive OK when backend sets active
Abuse control Minimal Required — limits per device

Example: all 10 get backend trial

user1@…  → Free Package, 7 days, 60 credits, free_trial_status=1
user2@…  → Same (same device_token OK)
…
user10@… → Same

After 7 days each user independently → inactive → must pay (one store sub per store account still applies at conversion).

Abuse controls (recommended)

  • Max N trials per device_token
  • Email verification before trial
  • Reduced credits for additional accounts on same device
  • Log device_token + user_id on registration

7. Android Base → Pro upgrade (proration)

For Base → Pro on Android, the app uses:

Purchases.PRORATION_MODE.IMMEDIATE_AND_CHARGE_PRORATED_PRICE
Meaning
IMMEDIATE Pro access starts right away
CHARGE PRORATED PRICE User pays price difference for remaining days in cycle
Same billing date Renewal day unchanged (e.g. still the 1st each month)

Example: Base ₹999/mo → Pro ₹1,999/mo, upgrade mid-cycle → ~₹484 charge today (illustrative) → full Pro ₹1,999 on next renewal.

Pro → Base uses DEFERRED — change at next billing date.

iOS uses plain purchasePackage; Apple handles proration in the subscription group.

8. Security, idempotency & checklist

Security

  • Verify RevenueCat webhook Authorization header
  • RevenueCat secret API key server only
  • Never trust client-sent package_name
  • Validate Restore / transfer against original app_user_id

Idempotency

  • Store event.id in revenuecat_webhook_events (unique index)
  • Re-fetch subscriber on every webhook
  • Prefer subscriber snapshot over event type when out-of-order

QA checklist (iOS + Android)

  • [ ] New user store trial
  • [ ] Trial → paid Base
  • [ ] Base → Pro immediate upgrade
  • [ ] Pro → Base deferred downgrade
  • [ ] Cancel → active until expiration
  • [ ] Expiration → SubscriptionGate
  • [ ] Monthly renewal + credits
  • [ ] Ten accounts same device (store vs backend trial behavior)
