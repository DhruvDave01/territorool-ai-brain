# Brain confidence score: how much an agent can trust this brain today

`node tools/brain-confidence.js` computes it. Every point comes from a measured signal; nothing is typed in by hand.
Rubric fixed on 2026-09-17, **before** the first computed result (owner asked for a number that can be trusted, not
one that looks good). Changing a weight or a signal is an owner decision and gets a `decision` memory entry.

This is not `tools/brain-score.js`: that one measures what the brain **contains** per feature
(`brain/context/confidence-score.md`). This one measures whether the brain can be **trusted to run work**: what is
known, what was verified, what is remembered, how safe it is, and whether a team can use it.

## Reading the number

- **Owner-only signals (signal ids are lowercase so they never collide with brain IDs such as the D1–D5 coding rules).** Several can only move with an owner action:
  - e1 and E2: close the production-config incident; point the configs at staging.
  - f2 and F3: commit and push the brain.
  - f5: confirm the video backup.
  - c5: set up CI.

  The tool prints them separately as the **ceiling** reachable without the owner.
- **C (verified behaviour) is the hardest to raise honestly.**
  - `offline` and `visual` need the mobile app, which is blocked while its config points at production (INTAKE rule).
  - `regression` needs real previously-fixed defects to re-test.
  - A type becomes N/A only with a specific written reason (`territool-test` §2).
- **Never raise a score by editing a signal's source to look green** (Law 7). A signal that is wrong is fixed in the
  tool, recorded with a `correction` memory entry, and the rubric date is updated.
