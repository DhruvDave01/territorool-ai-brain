# Tooling: which agent runs the brain, and what each one needs

The brain is **tool-agnostic**. Claude Code, Codex, Cursor, Copilot or a plain terminal can all drive
it, because every gate and suite is a plain shell command (**D-T1**, `brain/audits/05-testing.md` §2).
What changes per tool is only *which file it reads for instructions*.

This note is the source of truth for three things: the supported tools, what each needs before it can
work, and the handoff contract between them. The executable version of the setup checks is
`tools/doctor.js` — if the two ever disagree, the doctor is right and this note is stale.

---

## 1. Supported tools

Every tool reads the **same brain**. Only the entry file differs, and all of them are generated from
`brain/context/agent-brief.md` by `node tools/sync-agent-files.js`, so they cannot drift apart.

| Tool | Reads | Generated by us | Needs |
|---|---|---|---|
| **Claude Code** | `CLAUDE.md` + `.claude/skills/` (symlink to `brain/skills/`) | `CLAUDE.md` is hand-written; skills are real | `claude` on PATH, node (minimum: `stack.md` §0) |
| **Codex** | `AGENTS.md` | ✅ `AGENTS.md` | `codex` on PATH, node (minimum: `stack.md` §0) |
| **Cursor** | `.cursor/rules/*.mdc` (+ `AGENTS.md`) | ✅ `.cursor/rules/territool-brain.mdc` | Cursor app; `cursor` CLI optional |
| **GitHub Copilot / VS Code** | `.github/copilot-instructions.md` | ✅ | VS Code + Copilot |
| **Anything else** | `AGENTS.md` | ✅ | it is plain Markdown; point the tool at it |

**Rule:** never hand-edit `AGENTS.md`, `.cursor/rules/territool-brain.mdc` or
`.github/copilot-instructions.md`. They are overwritten. Edit `brain/context/agent-brief.md` and re-run
the sync.

## 2. What a member is asked, and what is checked

Before any work starts, the brain asks **which tool you are coding with** and **which tool runs tests**,
then verifies that setup actually exists rather than assuming it. That is `node tools/doctor.js`.

The answer is remembered per member in `.local/profile.json` (gitignored — it is personal, not team
state), so the question is asked once, not every session.

### Baseline — required for everyone

| Check | Requirement | Fix if missing |
|---|---|---|
| node | minimum in `stack.md` §0 (`node-min`); `doctor.js` reports the installed version | install Node |
| git | any recent; `doctor.js` reports the installed version | install git |
| `repos/mobile` | symlink resolves to a real React Native checkout | see §4 |
| `repos/web` | symlink resolves to a real Laravel checkout | see §4 |
| `.local/test-accounts.md` | exists, `chmod 600` | ask the owner; never commit it |

### Per-tool

| Tool | Check | Fix if missing |
|---|---|---|
| Claude Code | `claude` on PATH | install Claude Code |
| Codex | `codex` on PATH | install the Codex CLI, or add the app's binary to PATH |
| Cursor | `/Applications/Cursor.app` | install Cursor. The `cursor` CLI is optional — *Cmd-Shift-P → Shell Command: Install 'cursor'* |
| Copilot | VS Code installed | install VS Code + the Copilot extension |

### Per-job — only checked when the job needs it

| Job | Check | Fix if missing |
|---|---|---|
| Mobile lint / types / unit | `repos/mobile/node_modules/.bin/{eslint,tsc,jest}` | `yarn install` in the mobile repo (owner approval — S0.3) |
| Web syntax + unit | `php` (target: `stack.md` §0), `repos/web/vendor/bin/phpunit` (version: `stack.md` §0) | install the target PHP / `composer install` |
| API contract suite | node only — **no dependencies** | nothing |
| Web E2E | `tools/ms-playwright/` present | `PLAYWRIGHT_BROWSERS_PATH=$PWD/ms-playwright npx playwright install chromium` in `tools/` |
| Mobile E2E | `maestro` on PATH + a **second** simulator | install Maestro (owner-approved on demand). Never the user's booted simulator (S0.7) |

## 3. Handoff contract — Codex runs, Claude checks (USER SAID 2026-09-16)

The owner's split: **Codex executes, Claude Code reviews and owns the brain.** This is not an
arbitrary division — the loop (`brain/skills/territool-router/LOOP.md` §7, formerly `territool-loop` §5) requires gate verification to happen in a context that never
saw the build reasoning, and a different tool in a different process is a stronger guarantee of that
than a subagent of the same model.

### Who may do what

| | Claude Code | Codex |
|---|---|---|
| Write `brain/**` | ✅ **only Claude Code** | ❌ never |
| Run `tools/brain-sync.js` | ✅ | ❌ |
| Write `workspace/tasks`, `qa-reports`, `loop` | ✅ | ❌ |
| Write `workspace/handoff/**` | reads it | ✅ **this is Codex's area** |
| Run suites, gates, E2E | ✅ | ✅ |
| Edit `repos/**` | ✅ inside an explicit task | ✅ inside an explicit task |
| Commit or push | ❌ unless asked | ❌ never |
| Touch production | ❌ | ❌ |

**Why the single-writer rule matters:** the Obsidian vault and the shared graph are two renderings of
`brain/audits/data/brain-index.json`. They stay identical because one writer rebuilds the index after
every change. A second writer editing `brain/**` silently drifts the vault from the shared link until
someone re-runs the sync, and `tools/brain-parity.js` would start failing.

### The exchange

```
Claude Code                          workspace/handoff/<date>-<slug>/        Codex
-----------                          --------------------------------        -----
writes the task brief + the  ──────► request.md   (exact commands,      ──►  reads, runs
exact commands to run                 scope, what NOT to touch)               nothing else

                                 ◄── result.md    (per command: exit    ◄──   writes
reads, verifies, writes the           code, output tail, verdict)             only here
QA report and updates the brain       + any *.json run reports
```

**Rules for the `request.md`:** every command is verbatim and runnable, with the working directory
stated. No command that has not been verified to exist (`tools/doctor.js`). Anything that spends
credits, purchases, syncs a CRM or touches production is out of scope and is never written into a
request.

**Rules for the `result.md`:** exit codes, not opinions. A command that was not run is `NOT RUN`, never
inferred. Credentials and tokens are never pasted in — suites read `.local/test-accounts.md` themselves
and redact their own output.

## 4. Setting the brain up on a new machine

```bash
node tools/brain-start.js          # asks which tools you use, checks them, syncs the brain
```

That is the only command a new member needs. It will:

1. ask which tool you code with and which runs tests (once — stored in `.local/profile.json`);
2. run `tools/doctor.js` and print exactly what is missing and how to fix it;
3. scan `shoebox/00-INBOX/` for anything new that has been dropped in;
4. rebuild the index, the shared graph and the Obsidian vault, and check they agree;
5. print what to read first and what is currently open.

**`repos/` are symlinks to absolute paths on the owner's machine and will not resolve on anyone
else's.** `brain-start` detects this and asks for the local checkout paths, then re-points the
symlinks. Nothing else in the brain hard-codes a machine path.

## 4b. Obsidian graph: colours, groups and the centre

`node tools/obsidian-sync.js` writes `.obsidian/graph.json` with 19 colour groups, keyed on the
`brain/kind/*` tag every generated note carries, so the vault is coloured **exactly** like the shared
D3 page — feature green, journey pink, recording orange, problem red, rule blue, check purple, owner
decision gold, screen cyan, screenshot steel, code grey, and the `_map/` hubs pure white.

- **The centre is `_map/Brain Home.md`** — the only white node, linking every area hub, every entity
  hub, all 32 features and all 22 journeys (81 links). Start there and the rest reads outward.
- **The default filter is `-tag:#brain/kind/code -tag:#brain/kind/capture -tag:#brain/kind/commit`**
  (updated 2026-09-17). It hides the three bulk groups (code files, screenshots, the 198 commit records
  in `brain/memory`) so the structure is visible. **Clear the filter box in the graph view to see everything.**
- **Tags and attachments are off** (`showTags`, `showAttachments`: false; unresolved links hidden).
  With them on, every image, stylesheet, font and tag becomes a dot: about 2,250 attachments form the
  loose ring around the graph, and tags add extra dots. The sync applies these defaults **once** per
  change of `VIEW_DEFAULTS_VERSION` (stamp: `.obsidian/.brain-view-defaults`), so a deliberate toggle
  in Obsidian survives later syncs.

### 4c. The hub map: the simple picture (2026-09-17)

The main vault links every note to every related note, which is right for tracing a fact and looks like
one dense blob. `node tools/hub-map.js` (run by `brain-sync`, checked by `brain-check`) draws the **same
index** as a tree instead: Home → 18 area hubs → the 32 features and 10 journeys → leaves, with **exactly
one link per note** (1,304 notes, 1,303 links). Rules live in `tools/lib/hubs.js`:

- a screenshot hangs from its journey; anything else that touches one or two features hangs from the
  feature it links to most; cross-cutting notes (three or more features) hang from their area hub;
- code files, brain scripts and commit records are left out (they stay in the full vault).

Two ways to see it:
- **Obsidian:** *Open folder as vault* → `territool-brain/views/hub-map/`, then open the graph view
  (bookmarked as *Hub map*). Each note has an *Open the full note* link back into the main vault. The
  main vault ignores `views/` (filter added by the sync), so the two never mix.
- **Shared page:** the **Hub map** button (`workspace/brain-graph/hub-data.js`). The page uses it only
  when it was built from the same index as `graph-data.js`, so a stale file cannot attach dots to the
  wrong parents.

`views/hub-map/` is generated: never hand-edit it.

> [!warning] Obsidian resets this file
> Obsidian rewrites `.obsidian/graph.json` whenever the graph settings panel is opened or the graph
> view closes, and it **empties `colorGroups`** when it does. It also uses hyphenated keys
> (`collapse-filter`), and silently drops any key it does not recognise — which is how the first set of
> colours was lost.
>
> The sync self-heals: if it finds `colorGroups` empty it puts them back and leaves your other graph
> tweaks alone. If the colours vanish, run `node tools/brain-sync.js`, then **close and reopen the
> graph view** (Obsidian only reads the file when the view opens). With Obsidian running, quit it first
> for a clean restore: `node tools/obsidian-sync.js --force-config`.

## 5. Adding anything to the brain

Drop it in **`shoebox/00-INBOX/`** — documents, screenshots, videos, exports, notes, anything.
`tools/inbox-scan.js` (run automatically by `brain-start`) reports what is new since it last looked and
suggests where each item belongs. It **never files anything automatically**: where a document belongs is
a judgement call, and a wrong auto-file is harder to notice than an unfiled one.
