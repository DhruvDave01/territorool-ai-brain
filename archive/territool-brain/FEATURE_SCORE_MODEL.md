# FEATURE_SCORE_MODEL — how `tools/brain-score.js` computes feature task confidence

Reverse-mapped from `tools/brain-score.js` + `brain/context/confidence-score.md` (2026-09-16). The scorer is
**read-only** for this loop. This document exists to find *genuine* missing evidence, never to game the number.

## Inputs the scorer reads

| Source | Used for |
|---|---|
| `brain/audits/data/brain-index.json` (nodes + links) | code, behaviour, parity per feature `id:Fxx` |
| `workspace/test-cases/` filenames | tests (cases half) |
| `workspace/test-suites/**` filenames (walked; `lib/` and dotdirs skipped) | tests (suite half) |
| `workspace/qa-reports/*.md` filenames + first `Verdict:` line | qa |
| `brain/context/flows.md` | criticality per feature (weight) |

## The five dimensions (20 points each = 100 per feature)

| Dimension | Weight | 20 pts | 10 pts | 0 pts | How the brain gets it | Legitimate improvement |
|---|---:|---|---|---|---|---|
| **Code** | 20 | a `code` node is linked to `id:Fxx` in the index | only a `screen` node linked | nothing | brain-graph links web classes whose served routes match a flow's entry-point globs (`flows.md` col 5), and mobile screens named in col 4 | give a feature accurate concrete entry points in `flows.md` so brain-graph links its real code |
| **Behaviour** | 20 | a `capture` (screenshot) or `video` node linked | only `mflow` (journey) or `screen` | nothing | screenshots come from `owner-mobile-captures.json` / `web-screenshots.json`; videos from `mobile-videos.json`; journeys from `mobile-flows-captured.md` | index real runtime/owner screenshots for the feature |
| **Parity** | 20 | `parity-map.md` status matches `/owner-confirmed\|identical\|only\|n\/a/` | anything else (e.g. "accidentally different") | text contains `UNVERIFIED` or `*proposed*` | `parity-map.md` status column | verify an UNVERIFIED/proposed row against real evidence and record a settled status **with the evidence** |
| **Tests** | 10+10 | a `workspace/test-cases/Fxx-*` file **and** a `workspace/test-suites/**/Fxx-*` file | one of the two | neither | file names starting with the feature id | write real test cases + a runnable suite whose basename starts with `Fxx-` |
| **QA** | 20 | a `workspace/qa-reports/<date>-fxx-*.md` whose first `Verdict:` line is `PASS` or `PASS-WITH-NOTES` | — | no such file, or the verdict is FAIL/PARTIAL | one report file per feature | run the feature's suite / runtime QA and write a report with an honest passing verdict |

**Overall** = Σ(weight×score) / Σ(weight), weight = BLOCKER 4 · HIGH 3 · MEDIUM 2 · LOW 1.

## Zero / partial / full, precisely

- **Zero code/behaviour** = no linked node of that group. Fix by making the *index* link real code/screens — i.e. accurate mapping, not placeholder files.
- **Parity 0** is caused *only* by the literal strings `UNVERIFIED` or `*proposed*` in the status. Removing them is legitimate **only** after real verification; otherwise it is gaming.
- **Tests** count by **file name prefix**, not content — so an empty file would score. That would be gaming (§23). Every suite file here runs real cases; every case doc mirrors an executed suite.
- **QA** counts only if the first `Verdict:` line is PASS/PASS-WITH-NOTES. A `PARTIAL`/`FAIL`/`BLOCKED` verdict scores 0 — so a feature that genuinely cannot be verified (e.g. F15 buy-contacts, payment-blocked) **must not** get a passing report; it stays 0 and that is correct.

## What each dimension can and cannot reach in this environment

| Dimension | Ceiling without app changes / paid access |
|---|---|
| Code | 20 for every feature with discoverable implementation (all but pure-system F04 partial) |
| Behaviour | 20 where a screen exists and can be captured; **0 legitimately** for headless features (F04 crons) |
| Parity | 20 where evidence settles it; stays 10 for verified-but-unfixed divergences (BT targets); stays 0 where only the owner can confirm a *proposed* difference |
| Tests | 10–20 where a **non-mutating** contract or runtime test exists; hard for features whose only actions mutate data or spend credits (F15, F17 send, F07 provider cost) |
| QA | 20 where a suite/runtime run passed; **0 (correctly)** where runtime is payment/CI/captcha-blocked (F03 pay step, F15, F25 Admin HQ runtime) |

## Consequence for the target

A weighted 90 requires most BLOCKER/HIGH features near 90. The hard caps are: **F15** (buy contacts — payment/mutation blocked: no tests, no runtime QA → max ~60), **F03/F04** (payment/system), **F25** (Admin HQ runtime behind a captcha). These are **documented external blockers**, so the honest report gives both the actual score and the reachable ceiling (§28 of the brief).
